## 第二章 深度思考过程与解决思路

### 2.1 问题定义：真正的难点不是"造数据"

初看任务 2 是"造一批标注数据"。但按这个理解做，产出的东西在论文和甲方评审中都经不起问。真正的难点有四个，且互相耦合：

1. **粒度**：检索单元定为什么？定了就不能改，改了 qrels 全部作废。
2. **成本**：全库逐条判定不现实，如何在有限预算内让判定覆盖有意义的部分？
3. **可信度**：标注员之间不一致怎么办？多大不一致算不合格？
4. **统计功效**：只有几十个主题时，"A 比 B 高 0.03"到底算不算更好？

这四个问题在 IR 评测领域恰好都有七十年的成熟答案。因此核心思路确定为：**不发明方法，迁移方法**。

### 2.2 决策一：检索单元定在构件级

列出三个候选并比较：

| 方案 | 单元 | 判定可行性 | 与甲方任务的对应 |
|---|---|---|---|
| A | 整张图纸 | 粒度太粗，"这张图是否回答了 DN300 检查井的查询"难以判定 | 图纸归档检索 |
| B | **构件 / 图元（一个井、一段管）** | **每个单元可独立判定相关性** | **与"井与管段参数标注"对象一致** |
| C | 属性块 / 标题栏条目 | 上下文丢失，判定困难 | 字段出处追溯 |

选 B。决定性理由是判定可行性——评测集的每一条判定都必须能被标注员无歧义地回答，而图纸级做不到。

同时规定 docid 命名沿用 `#` 分段约定（`图纸编号#构件序号`），与任务 1 中 TREC segment 级工具链对齐，便于直接复用校验脚本的粒度检查。

### 2.3 决策二：用 pooling 把成本压到可承受

全库 500 条构件 × 30 主题 = 15,000 条判定，按 30 秒/条约 125 人时，不现实。

采用 TREC 的 pooling：只判各系统 Top-k 汇总去重后的文档。用 3 个系统 × Top-20，实测池子 1,742 条，降至约 14.5 人时/人，**成本降到十分之一以下**。

配套决定：**必须注入种子正例**。否则某些难主题的池子可能全为负例，导致该主题所有系统都得 0，既浪费标注量又扭曲均值。

### 2.4 决策三：一致性用加权 κ，门槛 0.6

相关性等级是**有序**的（0<1<2<3），未加权 Cohen's κ 会把"0 vs 1"和"0 vs 3"同等对待，系统性低估一致性。因此主判据定为**二次加权 κ**，门槛 0.6。

这一选择也决定了脚本要同时输出三种统计（完全一致率、相邻一致率、严重分歧率），因为诊断时看的是分歧的**形态**而非单一数字。

另一个判断：**κ 不达标时，九成原因是 narrative 写得有歧义，不是标注员不认真**。因此把 narrative 的写法规范提升到方案的核心位置，并单列一份可直接发给标注员的指南。

### 2.5 决策四：显著性检验是硬要求

自建集通常只有 30–60 个主题。这个样本量下，均值差 0.03 通常不显著。若只报均值，等于说了等于没说，且容易被质疑。

因此把 paired bootstrap 作为交付的一部分（而非建议）。实测合成数据：A=0.3269 vs B=0.3615，差值 −0.0346，95% CI [−0.1010, +0.0325]，p=0.3068 → 不可宣称更优。这个数值本身就是最好的说服材料。

### 2.6 决策五：把坑固化成脚本，而不是写进文档

文档里写"注意粒度一致"没有人会照做。把检查项写进 `check_format.py`，让它自动报错，才有可能真正生效。同理，qrels 体检（无正例主题、主题数不足、等级分布倾斜）也做成脚本自动告警。

### 2.7 执行路径

```
问题定义（难点不是造数据，是方法学）
        ↓
决策1：检索单元 = 构件级
        ↓
决策2：pooling 控成本 + 种子正例
        ↓
决策3：加权 κ ≥ 0.6 + narrative 规范化
        ↓
决策4：paired bootstrap 显著性
        ↓
合成数据（30 主题 / 500 构件）端到端跑通三个脚本
        ↓
与任务 1 工具链打通（qrels 直接喂给官方指标脚本）
        ↓
撰写方案文档 + 标注规范模板
```

## 第三章 国内外评测竞赛的前世今生（方法学溯源）

任务 2 的全部方法都来自这条脉络。理解它，才知道自建时哪些能省、哪些绝不能省。

### 3.1 Cranfield 范式：一切的起点（1950s–1966）

英国 Cranfield 航空学院 Cyril Cleverdon 团队的工作确立了现代检索评测的基本范式：

| 要素 | Cranfield 的做法 | 今天的状态 |
|---|---|---|
| 测试集 | 1,398 篇航空学论文摘要 | 规模扩大数个数量级，形式不变 |
| 查询集 | 225 条 | 形式不变 |
| 判定 | 穷尽式，每个（查询, 文档）对都判 | **大规模下已不可行** |
| 指标 | 查全率、查准率 | 仍是基础 |

Cranfield 的核心遗产是：**用固定的文档集 + 固定的查询集 + 固定的标准答案，在受控条件下比较系统**。自建评测集必须遵守这一条，否则无从比较。

### 3.2 TREC 与 pooling 的诞生（1992 起）

1990–1991 年，DARPA TIPSTER 项目委托 NIST 的 Donna Harman 构建 2 GB 级测试集。NIST 提议以此召开评测会议，1992 年首届 TREC 召开，25 个团队参与，任务是把系统从检索 2 MB 扩展到 2 GB。

规模一上来，穷尽判定立即失效。TREC 的答案是 **pooling**：

> 把各参赛系统返回的 Top-k 结果汇总去重，只对这部分文档做人工判定；未出现在池中的文档在评测时视为不相关。

这一设计让大规模评测成为可能，代价是引入 **pool bias**——新系统召回池外文档会被系统性低估。这个偏差无法消除，只能承认并在报告中声明。

TREC 1992–1999 的 Ad hoc 测试集合计约 189 万篇文档、450 个主题，每届 50 个主题、每主题提交 Top 1000。这些数字成为后续自建集的尺码参照。

### 3.3 全球扩散：CLEF、NTCIR、FIRE、TAC

| 机构 | 起始 | 对方法学的贡献 |
|---|---|---|
| **CLEF** | 2000 | 欧洲语言与跨语言检索评测；2010 年转为独立会议，2012 年 INEX 并入；形成 eHealth、LongEval、Touché、CheckThat!、SimpleText 等 lab |
| **NTCIR** | 1999 | 日本 NII 主办；从零构建日语、中文测试集，解决分词等语言差异；覆盖专利检索、_mathIR_、会话检索、金融等；2026 年 LREC 仍设"26 年历程"专题 |
| **FIRE** | 2008 | 南亚语言跨语言检索 |
| **TAC** | 2008 | NIST 主办，KBP、RTE、摘要，偏向文本分析而非排序 |
| **BioASQ** | 2012 | 生物医学专题挑战，每年多批测试集 |
| **COLIEE** | 2014 | 法律案例检索与蕴含 |
| **MS MARCO** | 2016 | 微软官方竞赛，Bing 真实查询日志；TREC DL 2019–2023 指定语料 |

**国内**：CCKS（中国中文信息学会）、NLPCC（CCF）、CCIR（CCF 全国信息检索学术会议）、SMP（CIPS 社会媒体处理专委）设有评测赛道；CCF BDCI、DataFountain、天池等使用企业真实搜索日志；早期 CWIRF 构建了中文网页测试集 CWT100G。国内赛事赛道变动大、数据多赛后不公开，适合参赛而不适合事后复现。

### 3.4 最近一次范式转移：LLM 判定（2024–2026）

TREC 2024 RAG Track 首次在正式评测中大规模用 LLM 生成标准答案。UMBRELA（开源的 Bing 相关性评估器复现）用 GPT-4o 以零样本方式对（查询, 段落）打 0–3 分。

官方流程为三段：

1. **相关性**：UMBRELA 自动打分生成 Auto Qrels → 人工后编辑生成 Post-Edited Qrels
2. **Nugget**：LLM 从相关段落自动抽取原子事实单元 → 人工增删改
3. **答案评测**：逐句判定支持度（0–2）、流畅度、nugget 覆盖度

NIST 2025 年 7 月的大规模研究（77 个 run、19 支队伍）结论：UMBRELA 自动判定与全人工判定在系统排序上 Kendall's τ 约 0.890，**可替代全人工用于 run 级比较**；人工介入未显著提升相关性；人工评估员比 UMBRELA 更严格。

**对任务 2 的直接价值**：自建评测集可以采用"LLM 预打标 + 人工只仲裁分歧"的路线，把标注成本再压一个数量级。这是方案的可选扩展，但未写入默认流程——因为首次建集仍建议用纯人工建立可信基线，待人工基线稳定后再引入 LLM 并测量其与人工的一致性。

### 3.5 演进规律与自建时的取舍

| 时期 | 判定方式 | 主指标 | 自建时可否简化 |
|---|---|---|---|
| 1960s | 穷尽判定 | P / R | 判定方式不可（成本不允许） |
| 1992–2015 | pooling + 人工 | MAP、nDCG | **方法学不可简化** |
| 2016–2022 | pooling + 人工 | nDCG@10、MRR | 不可简化 |
| 2024– | LLM 判定 + 人工后编辑 | nDCG、nugget 覆盖 | 可作为第二阶段降本手段 |

结论：**pooling + 分级判定 + 官方指标这三件套是自建集不可省的最小集**，省掉任何一件，评测结果就不可比、不可信。

```

                                                            ↓
⑦ 评测 + 显著性 ← ⑥ qrels 体检 ← ⑤ 双人标注 + 一致性检验
```

| 步骤 | 工具 | 产出 |
|---|---|---|

### 4.2 为什么必须自建

## 第五章 评价数据集设计

### 5.1 Topics 设计

**数量**：最少 30，建议 40–60。低于 30 时组间差异基本不可能显著，脚本会直接告警。

**来源优先级**：

1. 甲方真实需求 / 历史查询日志（最有说服力）
2. 工程人员访谈整理的实际检索意图
3. 从图纸属性反向构造（保证有正解，但偏简单）

**三要素结构**（缺一不可）：

```json
{
  "id": "101",
  "title": "钢筋混凝土检查井 DN300",
  "narrative": "需检索材质为钢筋混凝土、公称直径DN300的检查井，要求埋深参数明确且图纸来源可追溯；
                同类但材质或管径不符的判为弱相关(1分)；材质管径均符但埋深缺失的判为相关(2分)；
                材质、管径、埋深三项齐全且可定位到图号的判为完全匹配(3分)。"
}
```

**narrative 是整个标注质量的生命线**——它必须把"什么算 2 分、什么算 3 分"写到无歧义。κ 不达标时九成是 narrative 太粗。

**难度分布**：刻意保留 20–30% 的难查询（参数缺省、别名、跨图引用）。否则所有系统分数挤在一起，区分度为零。模板中给出 easy / medium / hard 三档示例。

### 5.2 Pooling 参数

| 参数 | 建议值 | 说明 |
|---|---|---|
| 参与系统数 | 3–4 | BM25（Lucene）、向量检索、混合（RRF / α 融合）、可选规则或属性过滤 |
| 每系统 Top-k | 20 | 池深 ≈ 系统数 × 20 × 去重率 |
| 种子正例 | 每主题 1–3 条 | **必须注入**，防止池子全负 |
| 随机负例对照 | 0（默认不开） | 能测漏召但标注量翻倍，预算充足时可对 20% 主题开启 |

**实测参考**（合成数据，30 主题 / 3 系统 / Top-20）：池子 **1,742 条**，平均 **58.1 条/主题**，按 30 秒/条约 **14.5 小时/人**，双人约 30 人时。真实场景按此量级做预算。

输出 CSV 已**打乱顺序并隐藏来源**，避免标注员按系统猜分。

### 5.3 标注规范

**四级制**（与 TREC DL 一致，可复用 `-l 2` 口径）：

| 分 | 含义 | CAD 场景示例 |
|---|---|---|
| 0 | 不相关 | 查雨水口却返回管段 |
| 1 | 弱相关 | 同为检查井，但材质或管径不符 |
| 2 | 相关 | 材质、管径命中，埋深缺失 |
| 3 | 完全匹配 | 关键参数齐全且可定位到图号 |

**边界情况处理**（最常出错处）：

- 同一张图的多个构件各自独立判定，不因同图已有高分项而降分
- 属性缺失按"未命中"处理，不脑补
- 数据明显异常仍按字面判定，在 `note` 列注明
- 无法判断不留空，按最接近等级给分并注明原因

**执行要求**：双人独立标注，标前做 20 条校准；一致性门槛二次加权 κ ≥ 0.6；分歧条目导出 `disagreements.csv` 交第三人仲裁后重跑。

### 5.4 与官方数据集的规格对照

| 维度 | TREC DL 2023 | TREC RAG 2025 | 本方案（CAD 自建） |
|---|---|---|---|
| 主题数 | 700 | 22（分批） | 30–60 |
| 语料规模 | 千万级文档 | 千万文档 / 亿级段落 | 视项目，通常万级构件 |
| 检索单元 | 段落/文档 | **segment** | **构件 / 图元** |
| 相关性分级 | 0–3 | 0–4（按子叙述数） | 0–3 |
| 判定方式 | pooling + 人工 | UMBRELA + 人工后编辑 | pooling + 双人人工 |
| 主指标 | nDCG@10 | nDCG@20/100、nugget | nDCG@10 |

规格对齐使自建集在方法学上可被直接审视，也让外部评审能用熟悉的标准衡量。

## 第六章 评测指标与统计显著性

### 6.1 指标选择

| 指标 | 用途 | 注意 |
|---|---|---|
| **nDCG@10** | 主指标 | 分级 qrels 首选 |
| MRR | 已知项检索 | 单答案场景 |
| P@5 | 首屏精确度 | 甲方最直观 |
| Recall@100 | 候选池质量 | **池子有限时有偏，慎报** |
| MAP | 整体排序质量 | 可并列报告 |

Recall 在自建集上尤其危险：池子只包含各系统 Top-k 的并集，理论最大召回被池子本身锁死，报出的 Recall 既不是真实召回，也不能跨集比较。主指标应落在 nDCG 与 P@k 上。

### 6.2 显著性检验（硬要求）

30–60 个主题属于小样本。只报均值等于没说。标配 **paired bootstrap**（对主题重采样，B=10000），辅以 paired t 检验。

**判读规则**：

- 差异的 95% CI 不含 0 且 p < 0.05 → 可宣称显著
- CI 跨 0 → 只能说"数值上更高"，不可宣称更优

**实测示例**（合成数据，30 主题）：

| 项 | 值 |
|---|---|
| A（BM25）nDCG@10 | 0.3269 |
| B（混合）nDCG@10 | 0.3615 |
| 差值 | −0.0346 |
| 95% CI | [−0.1010, +0.0325] |
| p 值 | 0.3068 |
| 逐主题胜负 | A 胜 13 / 负 17 |
| 结论 | **不显著** |

数值上 B 高 0.035，但 CI 跨 0、p=0.31，不能宣称"混合检索显著优于 BM25"。这类误判在小样本自建集上极常见。

### 6.3 一致性指标

| 指标 | 计算方式 | 用途 |
|---|---|---|
| 完全一致率 | A、B 打分相同的比例 | 直观但不区分分歧严重度 |
| 相邻一致率 | \|差\| ≤ 1 的比例 | 反映尺度是否稳定 |
| 严重分歧率 | \|差\| ≥ 2 的比例 | 直接指向规范缺陷 |
| Cohen's κ | 未加权 | 低估有序等级的一致性 |
| **二次加权 κ** | 权重 (|i−j|/range)² | **主判据，门槛 0.6** |

**实测**（注入 25% 相邻级噪声）：完全一致率 0.813、Cohen's κ 0.704、**二次加权 κ 0.844**、严重分歧率 0.000 → 判定达标。

### 8.3 汇报与论文写法要点

**必须写明的四句话**（缺一容易被质疑）：

1. 测试集规模：主题数、判定条数、检索单元定义、docid 规范
2. 构建方法：pooling（参与系统数、Top-k、去重后池深）
3. 标注质量：双人独立、二次加权 κ = X.XX、分歧仲裁机制
4. 统计口径：nDCG@10、相关性阈值 `-l 2`、paired bootstrap B=10000、显著性结论

**必须回避的两句话**：

- "在标准数据集上取得 SOTA" —— 自建集不是标准数据集
- 只报均值不报 CI / p 值 —— 小样本下等于没说

**关于 pool bias 的声明**（建议原文写入）：本测试集用于系统间**相对**比较，绝对分数不作为通用基线；池外文档按不相关处理，新系统召回池外文档时其分数被系统性低估。

## 第九章 风险与建议

| 风险 | 表现 | 规避 |
|---|---|---|
| **粒度中途变更** | 前期 qrels 全部作废 | 立项时一次性拍板，写入 docid 规范 |
| **主题数不足** | 差异永远不显著 | 起步不少于 30，目标 40–60 |
| **难度分布失衡** | 全简单题，所有系统分数趋同 | 强制保留 20–30% 难查询 |
| **narrative 含糊** | κ 不达标，返工重标 | 标前 20 条校准；κ 不达标先改规范 |
| **种子正例缺失** | 某主题池子全负，所有系统得 0 | 每主题强制注入 1–3 条 |
| **Recall 误用** | 报出自欺欺人的召回率 | 池子有限，主指标用 nDCG 与 P@k |
| **标注漂移** | 长时间停顿后尺度变化 | 分批连续完成，批次间做一致性抽查 |

**分阶段建议**：

- **第一阶段（本次交付）**：纯人工建立可信基线，规模 30–40 主题，产出可对外汇报的评测集
- **第二阶段**：基线稳定后引入 LLM 预打标，用人工基线测量其 Kendall's τ，达标后转为"LLM 预打标 + 人工仲裁分歧"，成本可再降一个数量级
- **第三阶段**：若需对外对标，可将同一套方法应用于 TREC 2026 官方赛道，形成"官方集 + 领域集"双轨证据
